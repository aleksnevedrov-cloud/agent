# Разбор: почему RFD-MESSENGER работает нестабильно (27.11.2026)

Повод: «Написать» из карточки в Telegram личный висит на «Отправляем…»; 25.11 — отправка в MAX по номеру «ушла»,
а чата нет; 17.11 — «Сервис мессенджеров недоступен» для VK; 15–16.11 — вложения и MAX. Разбор по коду ветки
`claude/new-session-vpbkn3` (на 27.11 — `c6837f7`), журналов сервера у разработчика нет.

## 1. Корневые причины (не отдельные баги)

| № | Причина | Как проявляется | Что сделано / что нужно |
|---|---|---|---|
| 1 | **Интерактивные пути без предела времени.** «Написать» = поиск номера в мессенджере → чат в amo → привязка → отправка. До 27.11 ни один шаг не ограничивался по времени, а Telegram личный (GramJS, MTProto через прокси) настроен на бесконечные переподключения: зависший запрос висел часами, занимал исполнителя канала, окно крутило «Отправляем…» | Скриншот 27.11; «Отправляем…» без конца | Сделано: предел на каждый шаг (поиск номера 15 с, amo 10 с, отправка 20 с) и общий предел задачи 60 с с ошибкой в талон; ошибка всегда с названием канала |
| 2 | **Сервер и виджет обновляются раздельно и несогласованно.** 17.11 сервер перешёл на асинхронную отправку (талон), а виджет в amoCRM остался старым: он принимал `{ticket}` за успех и показывал «Сообщение отправлено», хотя задача могла упасть | 25.11: «клиент не видит сообщение», «Чатов пока нет» | Сделано 25.11: сервер различает версии (`?v=2`); старый виджет ждёт результат в запросе. Нужно правило: сервер и `widget.zip` выкладываются одним шагом, версия видна в «Диагностике» |
| 3 | **Нет наблюдаемости у разработчика.** Каждый сбой превращается в переписку: я прошу команды для сервера, жду вывод, гадаю. Журналы на сервере, доступ только у заказчика | Любой инцидент решается 1–3 дня | Сделано: «Диагностика» в настройках виджета — версия сервера, каналы, очереди, исходящие за сутки, последние 60 сбоев обоих процессов, исходы последних «Написать»; всё без номеров и текстов, кнопка «Скопировать». Дальше — прислать этот текст вместе с жалобой |
| 4 | **Статус «Подключён» не означает «может отправить».** Для MAX по номеру (GREEN-API) и Telegram личного канал числится подключённым, пока жив инстанс/сессия, а отправка конкретному номеру может быть невозможна (номера нет в MAX, приватность Telegram, лимит checkAccount) | 16.11 MAX «Подключён», сообщения не доходят | Частично: ошибки теперь доходят до окна с причиной. Нужно (следующий шаг): проверка «живости» отправки раз в 5 минут (GREEN-API `getStateInstance` + `checkAccount` своего номера, Telegram `users.getUsers(self)`) и статус «подключён, но не отвечает» |
| 5 | **Хрупкие внешние зависимости в цепочке одного клика.** Прокси для Telegram/WhatsApp (переключение основной/запасной), GREEN-API (лимиты 466/429, медиа из облака), amoCRM REST (7 запросов/с) — четыре внешних сервиса на одну отправку | Разные симптомы в разные дни | Сделано ранее: очереди по каналам, 1 повтор ≤ 10 с, срок 2 мин, уведомления. Нужно: убрать из клика всё, что можно сделать заранее (см. п. 3 плана) |
| 6 | **Нет стенда приёмки.** Проверка идёт на боевом аккаунте с реальными клиентами, воспроизвести сбой нельзя, тестовые заявки потом удаляют | Повторные жалобы по одним и тем же сценариям | Нужен тестовый аккаунт amoCRM (или тестовая воронка) и тестовые номера в каждом мессенджере |
| 7 | **Несколько параллельных сессий разработки в одной ветке.** 22–23.11 в ветку легли коммиты других сессий (`d99ed44`, `773588b`), мои правки перебазировались поверх; никто не проверяет совместимость целиком перед выкладкой | Риск регрессий | Правило: одна сессия на этап; перед выкладкой — `pnpm check` на том коммите, который выкладывают |

## 2. Что именно происходит при «Написать» в Telegram личный (по коду)

1. Виджет: `POST /widget/v1/chats/start?v=2` → API проверяет канал и кладёт задачу `start-chat` в очередь `rfm-ch-<id>`, отвечает талоном за десятки мс.
2. Виджет опрашивает талон раз в 0,7 с до 30 с.
3. Исполнитель канала (процесс connectors): `connector.resolvePhone` → GramJS `contacts.ImportContacts` через прокси. Если прокси деградировал или MTProto в переподключении, вызов не возвращается. **До 27.11 — бесконечно.** Теперь — 15 с и ошибка «Telegram: поиск номера: нет ответа за 15 с».
4. Далее `createChat` и `linkChat` в amoCRM (теперь по 10 с), `send` (20 с), запись в талон.
5. Старый виджет вместо опроса талона ждёт ответ в самом запросе до 20 с (совместимость).

Если на сервере ещё не выложен коммит от 27.11, зависание на шаге 3 объясняет скриншот полностью. Если выложен,
а окно всё равно висит дольше 30 с, виновата сеть между браузером и сервером (nginx, CORS) — тогда в «Диагностике»
талон будет `done` или `error`, а окно его не получило.

## 3. План «чтобы работало достойно» (по приоритету)

| № | Шаг | Эффект | Объём |
|---|---|---|---|
| 1 | Выложить `c6837f7`+ (таймауты, диагностика, совместимость виджета) и **обновить виджет тем же днём** | Зависаний «Отправляем…» нет; любая ошибка видна текстом; есть что прислать разработчику | выкладка |
| 2 | При жалобе присылать текст «Диагностики» из настроек виджета | Разбор за минуты, а не дни | процесс |
| 3 | Проверка живости каналов раз в 5 минут и статус «не отвечает» с уведомлением в Telegram | Проблема видна до клика менеджера | 0,5 дня |
| 4 | Предварительный поиск номера: при открытии «Написать» для WhatsApp/Telegram/MAX проверять номер заранее и показывать «есть в MAX / нет» до нажатия «Отправить» | Клик «Отправить» делает только отправку, 1–3 с | 0,5 дня |
| 5 | Тестовая воронка/аккаунт и тестовые номера; чек-лист приёмки на 10 сценариев из ТЗ 17.11 | Сбои ловятся до клиентов | организационно + 0,5 дня |
| 6 | Telegram личный: рассмотреть отказ от прокси для MTProto (DC Telegram доступны из РФ не всегда стабильно, но прокси сейчас — главная точка отказа) или второй прокси другого провайдера; замерить долю ошибок по `stats` за неделю | Меньше зависаний у самого нестабильного канала | решение заказчика |
| 7 | Версионирование: `APP_VERSION` в образе (сделано), номер версии виджета в `manifest.json` печатать в «Диагностике»; сервер отклоняет виджет старше N | Несовместимые пары не живут незаметно | 0,3 дня |

## 4. Выкладка этого разбора

Сервер: `cd /opt/rf-messenger && git fetch origin && git checkout claude/new-session-vpbkn3 && git pull --ff-only && pnpm install --frozen-lockfile && pnpm build`, затем
`APP_VERSION=$(git rev-parse --short HEAD) docker compose build api connectors && docker compose up -d api connectors`.
Виджет: `widget/dist/widget/widget.zip` в интеграцию amoCRM тем же днём. Проверка: в настройках виджета раздел
«Диагностика» → «Показать» — версия сервера равна `git rev-parse --short HEAD`, каналы подключены, очереди пустые.
Откат: `git checkout 773588b`, та же сборка.
